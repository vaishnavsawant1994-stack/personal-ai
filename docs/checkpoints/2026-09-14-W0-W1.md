## W1 durable-storage guard

The production `personal-ai-runtime` Railway service has no persistent volume. Hosted startup now validates storage before `build_runtime()` opens production stores.

A hosted runtime requires:

1. `PERSONAL_AI_DATA_DIR` beneath `PERSONAL_AI_DURABLE_ROOT` (default `/data`).
2. A real non-root Linux mount containing the data directory.
3. A write + flush + `fsync` + read-back storage probe.

Failure raises `StorageUnavailable` and prevents the privileged runtime from starting on unproven ephemeral storage. Local/desktop operation remains unaffected.

## W1 encrypted backup implementation

Current evidence-supported status:

- IMPLEMENTED
- INTEGRATED
- AUTOMATED VALIDATED
- ISOLATED OPERATIONALLY VERIFIED
- NOT YET PRODUCTION/DURABLE-RAILWAY VERIFIED

Recovery behavior includes:

- AES-256-GCM authenticated encryption for newly created `.paibackup` archives.
- Per-backup key derivation via HKDF-SHA256 from the existing owner root-key architecture.
- Root key is never embedded in the archive.
- Safe SQLite online backup snapshots rather than blind copying of active database files.
- SQLite WAL/SHM/journal sidecars excluded from backup payloads.
- Archive path traversal, archive symlink and unlisted-payload defenses.
- Restore-destination confinement and existing-symlink rejection.
- Integrity metadata checks before restore.
- Full staged database integrity validation before any owner-data file replacement begins.
- Snapshot of existing restore targets before mutation.
- Failure-injected rollback of already-replaced files when a later replacement fails.
- Temporary fsynced replacement + `os.replace()` per restored file.
- Read-only legacy v1 backup compatibility; new backups are never plaintext.
- Wrong-key/tamper/live-WAL/rollback/symlink regression coverage.
