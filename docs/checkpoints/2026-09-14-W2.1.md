## Root causes repaired

### 1. Pending approvals were process-memory only

The previous approval manager and paused executor continuation were lost on process restart. A workflow or owner action waiting for approval therefore could not be safely resumed with the exact original intent after restart.

Repair:

- Added `trusted-actions.sqlite3` beneath the Personal AI data root.
- Added durable approval tickets and durable continuation checkpoints.
- Approval state now survives executor/process reconstruction when durable storage survives.

### 2. Approval scope was incomplete

The previous one-use ticket bound execution ID, tool name and exact parameter hash, but did not explicitly bind all identity/routing context required by the product directive.

Repair:

Each durable approval now binds:

- owner ID
- device ID
- session ID
- security epoch
- execution ID
- tool name
- exact parameter hash
- destination label
- data classification
- issue time
- expiry
- maximum use count = 1

Consumption is transactionally guarded with SQLite `BEGIN IMMEDIATE`, a pending-state predicate and a one-use counter.

### 3. Cloud relay dropped authenticated session identity

The cloud command path previously called the executor without forwarding the authenticated device/session identity, and approval redemption relied only on approval ID.

Repair:

- Cloud command now forwards authenticated device ID and cloud session ID into the executor.
- Cloud approval/rejection must match that same bound session/device.
- A second cloud session on the same trusted device cannot redeem the first session's approval.

### 4. Emergency Stop could leave stale approvals behind

Repair:

- Activating the authoritative tool Emergency Stop advances the durable approval security epoch and invalidates pending approvals.
- Cloud Emergency Stop synchronizes the global tool stop.
- Clearing Emergency Stop does not resurrect approvals that existed before the stop.

## Known limitations / remaining W2 work

W2 is still **PARTIAL**, not COMPLETE.

- PWA browser trust currently binds approvals primarily to trusted device identity; a durable first-class PWA session object still needs to be enforced across approval lifecycle.
- Tool execution still needs a generic verification-result contract and rollback metadata. A handler returning without exception is not sufficient final proof for consequential real-world actions.
- Dynamic destination/data-classification/risk policy requires deeper connector/tool integration.
- Critical actions still need uniformly enforced re-authentication policy.
- Audit tamper evidence/redaction still needs independent hardening.
- Pending approval data is durable but not yet separately application-level encrypted at rest; production disk encryption alone is not sufficient to mark this complete.
